# Handoff — produm clipboard copy default behavior

## Phase
Spec’ing / Designing → Handoff Generation

This document is the sole execution contract for this iteration.

---

## General description / context

The `produm` CLI currently generates a project dump file. The new requirement is to keep the existing default command behavior intact **and additionally copy the generated dump file contents to the system clipboard by default**.

Target UX:

- The basic command call (`produm`, or `produm .` if that is the current explicit form) should still generate the dump file as it already does.
- On successful dump generation, the command should also attempt to place the generated file contents into the user’s clipboard so the result is immediately pasteable into ChatGPT or another LLM/chat/client.
- Clipboard copy is a default behavior, not an opt-in flag, for this iteration.
- Clipboard failure must never make the overall dump command fail.

This iteration is intentionally narrow. It focuses on the default clipboard side effect only.

---

## Non-goals / Do Not Touch

### NG-260320_1-1
Do not redesign the existing dump-generation pipeline beyond what is required to access the final generated file content for clipboard copy.

### NG-260320_1-2
Do not add new output formatting modes such as “chat wrapper”, “LLM wrapper”, or fenced-code clipboard payloads in this iteration.

### NG-260320_1-3
Do not add clipboard-only mode.

### NG-260320_1-4
Do not add configuration files, persistent preferences, or environment-based user settings for clipboard behavior in this iteration.

### NG-260320_1-5
Do not fail the command because clipboard access is unavailable.

### NG-260320_1-6
Do not attempt complex remote-session, tmux, SSH-forwarding, or terminal-integration clipboard solutions in this iteration.

### NG-260320_1-7
Do not add size truncation logic unless required by an already-existing project constraint. Copy the full generated file contents.

---

## Locked decisions

### D-260320_1-1
Clipboard copy is **default behavior**.

### D-260320_1-2
What is copied to clipboard is the **generated file contents** (the file payload), not an alternate in-memory “raw dump object” representation and not a wrapped/prefixed chat template.

### D-260320_1-3
The program should **always attempt** clipboard copy after a successful dump.

### D-260320_1-4
Initial implementation strategy is **dependency-led / simple cross-platform support first**.

Preferred order:
1. Use a straightforward Python clipboard library if already aligned with the project.
2. Keep implementation simple and maintainable.
3. Avoid overbuilding Linux environment detection logic.

### D-260320_1-5
If clipboard copy fails, dump creation still succeeds and the user receives a clear warning.

### D-260320_1-6
For large files, copy the full generated file contents; no truncation in this iteration.

## Specs

### S-260320_1-1 — Default command behavior extension
The default dump command shall preserve its current primary behavior of generating the dump file and shall additionally attempt clipboard copy immediately after successful file generation.

#### S-260320_1-1.1
The dump file must still be written as before.

#### S-260320_1-1.2
Clipboard copy must occur only after the dump file has been successfully created and finalized.

#### S-260320_1-1.3
Clipboard copy must use the final contents of the generated output file.

### S-260320_1-2 — Clipboard success/failure semantics
Clipboard interaction is a best-effort secondary output target.

#### S-260320_1-2.1
If clipboard copy succeeds, the command reports success.

#### S-260320_1-2.2
If clipboard copy fails for any reason, the command must still exit as a successful dump operation, assuming file creation itself succeeded.

#### S-260320_1-2.3
Clipboard failure messaging must be explicit and user-visible.

#### S-260320_1-2.4
Clipboard failure must not produce a Python traceback in normal expected environmental failure scenarios.

### S-260320_1-3 — User-facing output
The CLI shall communicate both outcomes independently:
1. dump creation result
2. clipboard result

#### S-260320_1-3.1
On success, output should clearly indicate the dump file path.

#### S-260320_1-3.2
On clipboard success, output should explicitly say that clipboard copy succeeded.

#### S-260320_1-3.3
On clipboard failure, output should explicitly say clipboard was unavailable or copy failed, ideally with a short reason when available.

#### S-260320_1-3.4
Clipboard warnings should be non-fatal in wording and tone.

### S-260320_1-4 — Payload source of truth
The clipboard payload source of truth is the file written to disk.

#### S-260320_1-4.1
Implementation should read the generated file and copy that content.

#### S-260320_1-4.2
Implementation should not construct a second parallel clipboard payload path that could drift from the saved file content, unless strictly necessary for the current architecture.

### S-260320_1-5 — Platform support posture
The implementation must be practical and good-enough across common desktop environments without overcommitting to perfect clipboard support.

#### S-260320_1-5.1
The implementation should work on common local desktop environments where clipboard access is available.

#### S-260320_1-5.2
Headless Linux, remote SSH sessions, minimal containers, and similar environments may fail clipboard copy; this is acceptable as long as behavior is graceful.

#### S-260320_1-5.3
The implementation should prefer simple cross-platform mechanisms over Linux-display-server-specific logic.

### S-260320_1-6 — Backward compatibility
Existing user workflows that rely on the generated file must continue to work.

#### S-260320_1-6.1
File naming, location, and generation flow must remain unchanged unless a directly related bug is discovered.

#### S-260320_1-6.2
The new clipboard behavior must not alter the dump file content.

## Implementation

### I-260320_1-1 — Introduce clipboard helper
Add a small, isolated clipboard helper function/module responsible for:
- accepting text content
- attempting clipboard copy
- returning a structured success/failure result

Recommended shape:
- `copy_to_clipboard(text: str) -> ClipboardResult`
- where `ClipboardResult` captures success plus an optional reason/message

The exact type design is flexible, but the call site should not depend on exceptions for expected environment failures.

### I-260320_1-2 — Read from generated file
After the dump file is generated, read the file text back from disk and pass that exact content to the clipboard helper.

### I-260320_1-3 — Keep clipboard failure non-fatal
Wrap clipboard copy so that known clipboard/environment/tooling failures are converted into a warning result instead of crashing the CLI.

### I-260320_1-4 — CLI messaging
Adjust CLI output so users can see:
- dump created + path
- clipboard copied, or
- clipboard unavailable / failed (warning)

### I-260320_1-5 — Dependency approach
Use the simplest maintainable clipboard approach that matches the project’s packaging style.

Preferred direction:
- use a Python library for clipboard access if that is the lightest stable approach
- avoid implementing multiple manual OS-specific subprocess backends unless the chosen library proves inadequate during implementation

### I-260320_1-6 — No hidden regressions
Ensure that when clipboard support is unavailable, the only behavioral difference versus current behavior is an added warning line after successful file generation.

### I-260320_1-7 — Optional internal separation
If helpful for cleanliness, separate responsibilities into:
- dump generation
- output file resolution
- clipboard copy
- user notification

This separation is encouraged but not required if the codebase is still small.

## Tests

### T-260320_1-1 — Existing dump generation still works
Verify that the normal command still creates the expected dump file successfully.

### T-260320_1-2 — Clipboard success path
In an environment with clipboard access:
1. run the dump command
2. verify the file is created
3. verify the command reports clipboard success
4. paste clipboard content and confirm it matches the generated file content

### T-260320_1-3 — Clipboard failure path
In an environment without clipboard support, or by mocking clipboard failure:
1. run the dump command
2. verify the file is still created
3. verify the command does not fail because of clipboard
4. verify the command reports a warning

### T-260320_1-4 — Payload parity
Verify that clipboard payload equals the exact saved file contents, not a variant.

### T-260320_1-5 — Large dump sanity check
Run the command on a reasonably large project dump and confirm:
- file is created
- no truncation occurs in the saved file
- clipboard attempt occurs
- failure, if any, is graceful

### T-260320_1-6 — No traceback on expected environmental failure
Force or simulate clipboard unavailability and verify the CLI presents a warning rather than an unhandled exception.

## Definition of Done

### DoD-260320_1-1
Running the standard dump command still creates the dump file exactly as before.

### DoD-260320_1-2
After successful dump generation, the program automatically attempts clipboard copy.

### DoD-260320_1-3
The clipboard payload matches the generated file contents.

### DoD-260320_1-4
Clipboard failure does not fail the command.

### DoD-260320_1-5
The CLI clearly communicates both file creation and clipboard outcome.

### DoD-260320_1-6
No new chat-wrapper or alternate clipboard format is introduced in this iteration.

## Notes for execution agent

- Keep the implementation small.
- Favor reliability of overall CLI behavior over perfection of clipboard support.
- If the selected clipboard dependency introduces packaging or runtime complications beyond this handoff’s intent, stop and report rather than inventing a broader platform-abstraction layer.
- If an existing dependency already used by the project can satisfy clipboard support cleanly, prefer reusing it over adding a heavier new dependency.
